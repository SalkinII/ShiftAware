### Task 2: Config Round-Trip Fix (Configured Logic Lost)

**Problem:** After running algorithm, config appears lost in UI. Root cause: `DistributionSettings` stores `fairnessWeight` and `preferenceWeight` in `algorithmWeights` JSON, but the optimizer reads 4-factor weights (`preferenceMatch: 0.35, experienceBalance: 0.25, workloadFairness: 0.15, coreShiftCoverage: 0.05`) from the same field. Two different schemas in one JSON blob.

**Fix:**
- Map UI sliders to actual algorithm weights:
  - `fairnessWeight` (0-100) → controls `workloadFairness` + `experienceBalance` proportionally
  - `preferenceWeight` (0-100) → controls `preferenceMatch`
  - `coreShiftCoverage` stays fixed at 0.05
  - Normalize so all 4 weights sum to ~0.80 (leaving headroom)
- `handleSave()` writes canonical 4-factor format to `algorithmWeights`
- `loadConfig()` reverse-maps from 4-factor format to slider values
- `maxShiftsPerPerson` and `minRestHours` persist in `balanceThresholds` — thread to optimizer
- After algorithm run (success or failure), always re-call `loadConfig()` in UI
- `runAllocation()` must NOT mutate EventConfig during a run

**Files:**
- Modify: `app/admin/team/components/DistributionSettings.tsx` (save/load mapping, post-run reload)
- Modify: `lib/services/assignments.service.ts` (extract maxShiftsPerPerson from config)
- Modify: `lib/algorithm/optimizer.ts` (consume maxShiftsPerPerson as hard constraint)

### Task 3: Resting Period Constraint

**Problem:** `minRestHours` is saved in config but never consumed. `validateShiftOverlap()` uses hardcoded 15-minute buffer.

**Fix:**
- Extend `validateNoOverlaps()` to accept `minRestMs` parameter
- Change overlap logic: member's previous shift end + rest period overlaps next shift start → violation
- Thread from service: `balanceThresholds.minRestHours` → `minRestHours * 3600000` → optimizer → validator
- Add Phase 3 post-hoc validation: scan all member assignments chronologically, report violations where gap < minRestMs
- New function: `validateRestPeriod(memberId, state, allShifts, minRestMs)` in validator.ts

**Data flow:**
```
EventConfig.balanceThresholds.minRestHours (DB)
  → AssignmentsService.runAllocation() extracts it
  → runAssignmentAlgorithm() eventConfig.minRestMs
  → Phase 1 & 2: validateNoOverlaps(memberId, shift, state, allShifts, minRestMs)
  → Phase 3: validateRestPeriod(memberId, state, allShifts, minRestMs)
```

**Files:**
- Modify: `lib/algorithm/validator.ts` (extend validateNoOverlaps, add validateRestPeriod)
- Modify: `lib/algorithm/optimizer.ts` (thread minRestMs to validation calls, add Phase 3 rest check)
- Modify: `lib/services/assignments.service.ts` (extract minRestHours from config)

### Task 5: Allocation Rules Enforcement in Algorithm

**Problem:** Rules persisted in DB (v3.5b) but never consumed by optimizer. Need generic, attribute-based constraint enforcement.

**Constraint model:**
- Rule: `{ shiftType, attribute, operator, value }`
- Meaning: "For shifts of type X, members MUST have attribute Y <operator> Z"
- **Direct enforcement (filter):** Members not matching are filtered OUT of candidates
- **Complementary enforcement (per-shift):** At least ONE member on each matching shift must satisfy the rule. If member A has `firstAid=false`, member B on same shift must have `firstAid=true`

**New file: `lib/algorithm/rule-validator.ts`**

Pure functions, no Prisma, no HTTP:

```typescript
interface AllocationRule {
  id: string;
  shiftType: string;      // template type to match
  attribute: string;       // attribute name
  operator: "EQUALS" | "NOT_EQUALS" | "CONTAINS";
  value: string;           // expected value
}

// Does this member's attribute satisfy the rule?
evaluateRule(rule: AllocationRule, memberAttrMap: Map<string, string>): boolean

// Filter candidates: remove those who violate hard rules for this shift type
filterByRules(
  candidates: { member, score }[],
  shiftTemplateType: string,
  rules: AllocationRule[],
  memberAttributes: Map<string, Map<string, string>>
): filtered[]

// Post-hoc: does each shift have complementary coverage?
validateComplementaryRules(
  state: AssignmentState,
  shifts: ShiftWithRelations[],
  rules: AllocationRule[],
  memberAttributes: Map<string, Map<string, string>>
): ConstraintViolation[]
```

**Operator implementation:**
- `EQUALS`: `attrValue === rule.value`
- `NOT_EQUALS`: `attrValue !== rule.value`
- `CONTAINS`: `attrValue.includes(rule.value)` (for multiselect/text)

**Integration into optimizer:**
- Phase 1 (preference matching): after overlap/capacity checks, check `evaluateRule()` per member
- Phase 2 (score-based filling): `filterByRules()` before scoring candidates
- Phase 3 (validation): `validateComplementaryRules()` for each shift
- Thread: `AssignmentsService` extracts `allocationRules` from `event.config`, passes via extended `eventConfig`

**Files:**
- Create: `lib/algorithm/rule-validator.ts`
- Modify: `lib/algorithm/types.ts` (add AllocationRule type to eventConfig)
- Modify: `lib/algorithm/optimizer.ts` (integrate rule filtering in Phases 1, 2, 3)
- Modify: `lib/services/assignments.service.ts` (pass allocationRules to optimizer)

## v3.10 — Advanced Constraints (1 task)

### Task 1: Generic Attribute Balance Constraints

**Problem:** `validateGenderBalance()` in `validator.ts` is hardcoded to "gender" attribute with fixed 50:50 ratio. v3.8 Task 5 introduces generic rule enforcement — this task extends it with configurable ratios.

**Design:**
- Extend allocation rule schema with optional `balanceMode`:
  - `"REQUIRE_ONE"` (default): at least one member must match — already in v3.8
  - `"REQUIRE_RATIO"`: configurable min/max ratio per shift
- Add `balanceMode?: string`, `minRatio?: number`, `maxRatio?: number` to rule schema
- Extend `validateComplementaryRules()` to handle ratio enforcement
- **Deprecate** hardcoded `validateGenderBalance()` — remove from optimizer Phase 3, replace with generic rules
- Update DistributionSettings UI: when adding a rule, allow choosing balance mode + ratio inputs

**Files:**
- Modify: `lib/algorithm/rule-validator.ts` (extend with ratio mode)
- Modify: `lib/algorithm/validator.ts` (remove validateGenderBalance)
- Modify: `lib/algorithm/optimizer.ts` (remove genderBalance call from Phase 3)
- Modify: `lib/validations/event-config.ts` (extend rule schema)
