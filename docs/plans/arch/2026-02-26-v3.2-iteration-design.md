## Section 1: Service Architecture Fixes (CRITICAL)

### 1A. Assignment Wiring — Event-Scoped Member Filtering

**Problem:** `runAllocation()` in `lib/services/assignments.service.ts` queries `prisma.teamMember.findMany({ where: { isActive: true } })` — loads ALL members instead of event-registered members.

**Fix:**
- Replace global member query with event-scoped query via `EventRegistration`:
  ```
  EventRegistration WHERE eventId = :eventId
    → include member with preferences and assignments
  ```
- Extract `member` objects from registration results
- Apply same pattern in `createManualAssignment()`: validate member has EventRegistration before allowing assignment
- In `swapAssignments()`: filter `findAll()` by event via `shift.eventId`

**Files:**
- `lib/services/assignments.service.ts` — `runAllocation()`, `createManualAssignment()`, `swapAssignments()`
- `lib/repositories/assignment.repository.ts` — add event-scoped `findByEvent(eventId)` method

### 1B. Transaction Safety

**Problem:** `deleteByEvent()` + `bulkCreate()` are separate calls. If insert fails, deletes aren't rolled back. Error: "Cannot rollback: missing required assignment fields."

**Fix:**
- Wrap both operations in a single `prisma.$transaction()` inside `runAllocation()`
- Delete + insert become atomic
- If insert fails with missing fields, the delete is rolled back

**Files:**
- `lib/services/assignments.service.ts` — `runAllocation()` (wrap steps 8+ in transaction)

### 1C. Event Mutation Guard

**Problem:** `updateEvent()` has no status check. Dates can change after shifts are planned.

**Fix:**
- Add `"EVENT_MUTATE"` to `GuardAction` type in `lib/services/event-status-permissions.ts`
- Set `EVENT_MUTATE: true` only for `PLANNING`, `false` for all other statuses
- Call `assertEventStatusAllows(eventId, "EVENT_MUTATE")` in `events.service.ts` `updateEvent()`
- Add `canMutateEvent(status)` client-safe helper for UI form disabling

**Files:**
- `lib/services/event-status-permissions.ts` — add guard action
- `lib/services/events.service.ts` — add guard to `updateEvent()`

## Section 3: UX Improvements

### 3A. Continuous Dynamic Reveal for Shift Nodes

**Problem:** Fixed zoom tiers waste visible space. Attributes should fill available area in priority order.

**Key insight:** The `scale(1/zoom)` trick means the inner content area is always `nodeWidth × SHIFT_NODE_HEIGHT` CSS pixels. The variable is **width** (shift duration × PIXELS_PER_HOUR), not zoom. Zoom only affects visual size on screen, not CSS layout dimensions.

**Priority order:**
1. Member names (occupation)
2. Time range
3. Shift name
4. Desirability score
5. Staffing count (X/Y)
6. Staffed status badge
7. Avatars
8. Vote buttons

**Implementation:**
- Replace the 3-tier component structure (`OccupationContent`, `CoreContent`, `DetailedContent`) with a single `DynamicShiftContent` component
- Each attribute is a small component with a known minimum pixel footprint
- Use a flex-wrap container: items flow left-to-right, then top-to-bottom
- Items added in priority order; container uses `overflow: hidden` so nothing clips mid-character
- **Width-driven layout:** Narrow shifts (short duration) stack vertically; wide shifts (long duration) arrange laterally (e.g., names left, time+desirability right)
- Everything maintains `scale(1/zoom)` for constant readability at all zoom levels
- At max zoom-out: member names visible and readable (P1)
- As width grows: time, name, scores fill in naturally

**Files:**
- `components/features/LaneCalendar/nodes/ShiftBlockNode.tsx` — replace tier components with `DynamicShiftContent`

### 3B. Context-Aware Side Panel

**Problem:** Shift details and preference voting need the right-side panel; vote buttons hard to find at low zoom.

**Design:**
- Side panel content varies by event status:
  - **OPEN_FOR_PREFERENCES:** Shift details + large WANT/DON'T WANT buttons + current vote status + preference counts
  - **ASSIGNING/FINALIZED:** Shift details + assigned members + staffing status
  - **PLANNING:** Shift properties editor (existing)
- **"My Shifts" tab (user view):** List of shifts the member voted on or was assigned to
- Panel opens on shift click; canvas shrinks to accommodate (flex-row, existing pattern)

**Files:**
- `app/app/calendar/page.tsx` — enhance side panel with preference voting
- `components/features/ShiftPropertiesPanel/ShiftPropertiesPanel.tsx` — make context-aware
- Possibly new `ShiftPreferencePanel.tsx` for the voting UI

### 3C. Zero-Occupancy Shifts

**Problem:** Need capacity=0 shifts as general markers (wiring, event setup).

**Design:**
- **Schema:** Remove any min-capacity validation that prevents 0; allow `capacity: 0` on Shift
- **Service guards:**
  - `runAllocation()`: skip shifts where `capacity === 0`
  - `createManualAssignment()`: reject if shift capacity is 0
  - Preference voting: skip zero-cap shifts (nothing to vote on)
- **Template support:** Allow `defaultCapacity: 0` on ShiftTemplate
- **UI:** Same glass card, but staffing section shows muted "Marker" badge instead of X/Y count; no avatar section; no vote buttons

**Files:**
- `lib/services/assignments.service.ts` — guard against capacity=0
- `lib/services/shifts.service.ts` — allow capacity=0 creation
- `lib/validations/shift.ts` — update min capacity if constrained
- `components/features/LaneCalendar/nodes/ShiftBlockNode.tsx` — marker badge rendering

### 3D. Shared Cache Invalidation Pattern

**Problem:** Identity badge, templates, and assignments go stale after mutations.

**Design:**
- Identify current data-fetching pattern (SWR/useQuery cache keys)
- Create `useEventCacheInvalidation(eventId)` hook returning:
  ```
  invalidate(...scopes: ("shifts" | "assignments" | "templates" | "preferences" | "registrations")[])
  ```
- Each mutation hook calls the appropriate invalidation after success
- For identity badge (global, not event-scoped): separate `invalidateIdentity()` utility
- Apply to all existing mutation paths

**Files:**
- New: `hooks/useEventCacheInvalidation.ts` (or similar)
- All mutation hooks that call API endpoints
- Identity-related components
