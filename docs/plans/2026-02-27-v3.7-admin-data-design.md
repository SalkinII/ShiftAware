# v3.7 "Admin Data & Sidebar" Sprint Design

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement the plan generated from this design.

**Goal:** Fix attribute rules to use real event templates, add attribute prompt when adding members to events, unify admin member creation with shared CreateProfileForm, and add read-only profile cards on avatar click.

**Date:** 2026-02-27

---

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Attribute rules shiftType source | Fetch event templates via `/api/events/{id}/templates` | Single source of truth; admin sees actual template names |
| Attribute prompt on member add | Second modal step after registration POST | Non-blocking; attribute fill stays optional if no definitions exist |
| Admin create form | Reuse `CreateProfileForm` component | DRY; capabilities already removed in v3.5; event attributes handled |
| Profile card placement | Admin team manage, MemberListByEvent, ShiftPropertiesPanel assignment list | All admin contexts where member avatars appear |
| Profile card data | Basic info only (alias, avatar, exp level, capabilities) | No extra fetch needed; parent already holds the data |
| Profile card dismissal | Escape key + click outside | Standard modal UX |

## Sprint Tasks (4 tasks)

### Task 1: Bug #2 — Dynamic Template List in Attribute Rules

**Problem:** `DistributionSettings.tsx` shiftType dropdown is hardcoded to `SUPER / MOBILE_TEAM / STATIONARY`. These do not reflect the event's actual templates, so attribute rules reference phantom types.

**Fix:**
- Add `templates` state alongside `attributeDefinitions` state
- In `fetchAttributeDefinitions`, also fetch `/api/events/{id}/templates` and set `templates` state
- Replace the hardcoded `<option>` entries for shiftType with `templates.map(t => <option value={t.type}>{t.name}</option>)`
- Default new rule `shiftType` to `templates[0]?.type || ""` instead of hardcoded `"SUPER"`

**Files:**
- Modify: `app/admin/team/components/DistributionSettings.tsx`

---

### Task 2: Bug #11b — Attribute Prompt When Adding Member to Event

**Problem:** `MemberListByEvent.tsx` calls `POST /api/events/{id}/registrations` then stops. If the event has attribute definitions, those values remain unset for the newly added member, breaking attribute-based assignment rules.

**Fix:**
- After successful registration POST in `handleAddMember`, check if `attributeDefinitions.length > 0`
- If yes: instead of calling `loadMembers()` + `setShowAddPicker(false)` immediately, transition to an attribute step modal
- Attribute step modal: renders the same field types as `CreateProfileForm` (BOOLEAN, SELECT, MULTISELECT, TEXT) using `attributeDefinitions`
- On submit: POST to `/api/members/{memberId}/attributes` (or the equivalent event-attributes endpoint) with `{ eventId, attributes: Record<string, any> }`
- On complete (or if user skips): call `loadMembers()` + close modal
- Fetch `attributeDefinitions` alongside `allMembers` on mount/event change (already done in `DistributionSettings`; replicate here)

**Files:**
- Modify: `app/admin/team/components/MemberListByEvent.tsx`

---

### Task 3: Admin Team Create — Reuse CreateProfileForm

**Problem:** `app/admin/team/manage/page.tsx` has a 100-line inline create form with its own state, validation, and capability-selection logic. The user-facing `CreateProfileForm` was updated in v3.5 (capabilities removed, event attributes added). The two forms have diverged.

**Fix:**
- Import `CreateProfileForm` from `@/app/app/identity/components/CreateProfileForm`
- Replace the inline `<form>` JSX (lines ~518–627) with `<CreateProfileForm onSubmit={handleSubmit} />`
- Adapt `handleSubmit` to accept `ProfileData` from `CreateProfileForm` (alias, avatarId, experienceLevel, capabilities, eventId?, attributes?)
- Remove: `formData` state, `formErrors` state, `validateForm()`, inline field JSX, EmojiPicker import (if unused after), Select import (if unused), `formErrors` error display
- Keep: `showForm` toggle, the "Add Member" button, the "Cancel" path

**Files:**
- Modify: `app/admin/team/manage/page.tsx`

---

### Task 4: ProfileDetailCard — Read-Only on Avatar Click

**Problem:** Clicking member avatars does nothing in admin views. Admins cannot quickly see member details without leaving the page.

**Fix — new component:**
- Create `components/features/Identity/ProfileDetailCard.tsx`
- Props: `member: { id, alias, avatarId, experienceLevel, capabilities } | null`, `onClose: () => void`
- Renders as a centered modal overlay (backdrop + card)
- Content: large avatar emoji, alias (heading), experience level badge, capabilities as tag chips
- Dismissal: `onClick` on backdrop, `onKeyDown` Escape on document

**Fix — wire into consumers:**
- `app/admin/team/manage/page.tsx`: add `selectedMember` state; on avatar `onClick` set `selectedMember`; render `<ProfileDetailCard member={selectedMember} onClose={() => setSelectedMember(null)} />`
- `app/admin/team/components/MemberListByEvent.tsx`: same pattern
- `components/features/LaneCalendar/sidebar/ShiftPropertiesPanel.tsx`: in the assignments list, make the member avatar/alias clickable; add `selectedMember` state; render `ProfileDetailCard`

**Files:**
- Create: `components/features/Identity/ProfileDetailCard.tsx`
- Modify: `app/admin/team/manage/page.tsx`
- Modify: `app/admin/team/components/MemberListByEvent.tsx`
- Modify: `components/features/LaneCalendar/sidebar/ShiftPropertiesPanel.tsx`
