# Calendar Architecture Plan: Lane-Based Drop Zones

**Date:** 2026-01-25
**Status:** Planning
**Priority:** High (Core component for Stage 2 workflow)

---

## Problem Statement

Templates don't drop at the correct position because:
1. **DateDropZone only provides day granularity** - passes `YYYY-MM-DD`, not time
2. **No lane concept** - calendar is a flat timeline, not lanes per shift type
3. **No coordinate-to-time mapping** - can't convert mouse position to time
4. **Snap logic exists but isn't connected** - `lib/utils/snap.ts` works, but drop position is wrong

---

## Current Architecture

```
┌─────────────────────────────────────────────────────────────┐
│ CalendarView (Timeline)                                      │
├─────────────────────────────────────────────────────────────┤
│ DateDropZone (Day 1) │ DateDropZone (Day 2) │ DateDropZone  │  ← Day-level only
├─────────────────────────────────────────────────────────────┤
│ ┌──────────────────┐                                        │
│ │ Shift Row 1      │ (any type, sorted by time)             │
│ └──────────────────┘                                        │
│ ┌──────────────────┐                                        │
│ │ Shift Row 2      │                                        │
│ └──────────────────┘                                        │
│ ...                                                          │
└─────────────────────────────────────────────────────────────┘
```

**Problems:**
- Shifts are in a flat list, not grouped by type
- Drop zones span full height, no lane awareness
- Can't determine which shift type lane was targeted

## Target Architecture: Lane-Based Calendar

```
┌─────────────────────────────────────────────────────────────┐
│ LaneCalendarView                                             │
├───────────────┬───────────────┬───────────────┬─────────────┤
│ Time Scale    │ Day 1         │ Day 2         │ Day 3       │
├───────────────┼───────────────┼───────────────┼─────────────┤
│ MOBILE_TEAM_1 │ ■■■■■ ■■■■    │ ■■■■■■        │             │  ← Lane row
│               │ [DropZone]    │ [DropZone]    │ [DropZone]  │
├───────────────┼───────────────┼───────────────┼─────────────┤
│ MOBILE_TEAM_2 │ ■■■■          │               │ ■■■■■■      │  ← Lane row
│               │ [DropZone]    │ [DropZone]    │ [DropZone]  │
├───────────────┼───────────────┼───────────────┼─────────────┤
│ STATIONARY    │ ■■■■■■■       │ ■■■■■■■       │ ■■■■■■      │  ← Lane row
│               │ [DropZone]    │ [DropZone]    │ [DropZone]  │
├───────────────┼───────────────┼───────────────┼─────────────┤
│ EXECUTIVE     │       ■■■■    │               │             │  ← Lane row
│               │ [DropZone]    │ [DropZone]    │ [DropZone]  │
└───────────────┴───────────────┴───────────────┴─────────────┘
```

**Benefits:**
- Visual grouping by shift type (user's mental model)
- Drop zones per lane + day (precise targeting)
- Snap to end of previous shift in same lane
- Clear succession visualization

## Implementation Options

### Option A: New LaneCalendarView Component (Recommended)

**Create a new component** specifically for the schedule page drag-drop workflow.

```
components/features/Calendar/
├── CalendarView.tsx      # Existing: timeline for viewing assignments
├── LaneCalendarView.tsx  # NEW: lane-based for shift planning
├── LaneDropZone.tsx      # NEW: drop zone with time + type
└── DateDropZone.tsx      # Keep for backward compatibility
```

**Pros:**
- Clean separation of concerns
- Existing CalendarView untouched
- Purpose-built for drag-drop UX

**Cons:**
- New component to maintain
- Some code duplication

### Option B: Refactor CalendarView with Lane Mode

Add a `displayMode: "timeline" | "lanes"` prop to existing CalendarView.

**Pros:**
- Single component
- Reuses existing code

**Cons:**
- Increases complexity of already complex component
- Risk of breaking existing usage

### Option C: Hybrid - Time Detection with Type Selection

Keep current architecture, add modal to select shift type after drop.

**Pros:**
- Minimal changes
- Quick to implement

**Cons:**
- Worse UX (extra step)
- Doesn't match user's "drop into lane" mental model

## Recommended Approach: Option A

Create `LaneCalendarView` with these features:

### 1. Lane Structure
```tsx
interface Lane {
  type: ShiftType;
  label: string;
  color: string;
  shifts: Shift[];
}

// Group shifts by type
const lanes: Lane[] = [
  { type: "MOBILE_TEAM_1", label: "Mobile Team 1", color: "#0ea5e9", shifts: [...] },
  { type: "MOBILE_TEAM_2", label: "Mobile Team 2", color: "#8b5cf6", shifts: [...] },
  { type: "STATIONARY", label: "Stationary", color: "#22c55e", shifts: [...] },
  { type: "EXECUTIVE", label: "Executive", color: "#f59e0b", shifts: [...] },
];
```

### 2. LaneDropZone Component
```tsx
interface LaneDropZoneProps {
  date: Date;
  shiftType: ShiftType;
  existingShifts: Shift[];  // For calculating snap positions
  onDropPositionCalculated?: (time: Date, snapped: boolean) => void;
}

// Provides data:
{
  type: "lane-drop",
  date: "2026-07-15",
  shiftType: "MOBILE_TEAM_1",
  snapTargets: [Date, Date, ...],  // End times of existing shifts in this lane
}
```

### 3. Time Calculation from Pointer Position
```tsx
// When dropping, calculate time from x-position
function calculateDropTime(
  pointerX: number,
  containerRect: DOMRect,
  dayStart: Date,
  dayEnd: Date
): Date {
  const relativeX = pointerX - containerRect.left;
  const percent = relativeX / containerRect.width;
  const totalMs = dayEnd.getTime() - dayStart.getTime();
  const offsetMs = percent * totalMs;
  return new Date(dayStart.getTime() + offsetMs);
}
```

### 4. Integration with Snap Logic
```tsx
// In handleDragEnd:
const { snapped, time } = calculateSnapPosition(
  calculatedDropTime,
  laneDropZone.snapTargets,
  30  // 30 minute threshold
);
```

## Visual Design

### Lane Row
```
┌─────────────────────────────────────────────────────────────────┐
│ 🚶 Mobile 1  │ ████████ 08:00-14:00 │ ████████ 14:00-20:00     │
│              │ [2/3 filled]         │ [1/2 filled]              │
│              │                      │            ← drop zone →  │
└─────────────────────────────────────────────────────────────────┘
```

### Drop Zone States
- **Idle:** Transparent
- **Hover:** Light tint of lane color + dashed border
- **Over with snap:** Solid border at snap position, tooltip "Snap to 14:00"
- **Over without snap:** Solid border at pointer position, tooltip "Drop at ~15:30"

### Shift Blocks
- Color-coded by type
- Show time range
- Show fill status (assigned/capacity)
- Drag handle visible in edit mode

5. On drop: shift created at correct time, in correct lane
