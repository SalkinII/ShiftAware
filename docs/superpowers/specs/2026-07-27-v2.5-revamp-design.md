# ShiftAware v2.5 Revamp — Design Spec

**Date:** 2026-07-27  
**Branch:** `Feature-v2.5-Revamp`  
**Status:** Complete — Sub-project A tagged `v2.5-a-structural-refactor`; Sub-project B tagged `v2.5-b-distribution-control-center`

---

## Overview

v2.5 is a two-sub-project revamp. Sub-project A is a structural refactor with no user-visible changes. Sub-project B delivers the Distribution Control Center and fixes all enforcement gaps in the assignment algorithm. A ships before B — it provides the cleaner foundation B is built on.

---

## Sub-project A: Structural Refactor

**Status: DONE** (2026-07-27). Shipped on `Feature-v2.5-Revamp`, tagged `v2.5-a-structural-refactor`. Actual outcomes: service layer deleted; HOFs on all routes; EventRepository split into 4; cache trim; `useEventContext` wrapper deleted; ~462 tests green. Note: export landed in `lib/utils/export.ts` (not `lib/domain/export.ts`); audit in `lib/utils/audit.ts`.

### Goal

Remove ~900 net lines, eliminate the redundant service layer, extract repeated API boilerplate into composable wrappers, and split the oversized EventRepository into focused classes.

### Sequencing (within A)

1. **Phase 1** — Add HOF wrappers (zero logic change)
2. **Phase 2** — Delete services, migrate real logic to `lib/domain/`
3. **Phase 3** — Split EventRepository into 4 classes
4. **Phase 4** — Cleanup: useEventContext wrapper, cache trim, validation guard consolidation

Each phase is a reviewable commit. No phase mixes structural and logic changes.

### Architecture: Before → After

**Before:**
```
API Route (80–160 lines, repeated boilerplate)
  → Service (thin delegate + status guards)
    → Repository → Prisma
```

**After:**
```
API Route (20–40 lines, pure intent)
  wrapped in: withAuth() → withErrorHandling()
  → lib/domain/ (orchestration & guards)
  → Repository → Prisma
```

### Phase 1 — HOF Wrappers

Two new files in `lib/api/`:

**`lib/api/withAuth.ts`**
```typescript
export function withAuth(handler) {
  return async (req, ctx) => {
    if (!await isAuthenticated()) return createUnauthorizedResponse();
    return handler(req, ctx);
  };
}
```

**`lib/api/withErrorHandling.ts`**
```typescript
export function withErrorHandling(handler) {
  return async (req, ctx) => {
    try { return await handler(req, ctx); }
    catch (e) {
      if (e instanceof RepositoryError && e.code === "NOT_FOUND") return createNotFoundResponse();
      if (e instanceof StatusGuardError) return createErrorResponse(e.message, 409);
      if (e instanceof ZodError) return createErrorResponse("Validation failed", 400);
      return createErrorResponse("Internal error", 500);
    }
  };
}
```

**Usage in every route:**
```typescript
export const POST = withAuth(withErrorHandling(async (req) => {
  const body = schema.parse(await req.json());
  const result = await eventRepo.create(body);
  await createAuditLog({ ... });
  return createSuccessResponse(result);
}));
```

All 37 route handlers are updated. Services are not touched in this phase. Tests run as gate — all 546 must pass before moving to Phase 2.

**New unit tests:** 2–3 per wrapper (auth returns 401, error maps correctly, success passes through).

### Phase 2 — Service Deletion

**What gets deleted outright** (pure delegates, no real logic):
- `lib/services/ShiftsService` → routes call `ShiftRepository` directly
- `lib/services/ShiftTemplatesService` → routes call `ShiftTemplateRepository` directly
- `lib/services/AuditService` → `createAuditLog()` utility already exists, used directly

**What gets migrated to `lib/domain/`:**

| Service | Destination | What moves |
|---|---|---|
| `EventsService` | `lib/domain/event-status.ts` | Status transition guards, prerequisite checks |
| `PreferencesService` | `lib/domain/event-status.ts` | Status guards on preference mutations |
| `MembersService` | `lib/domain/members.ts` | Deactivation workflow, compound queries |
| `AssignmentsService.runAllocation()` | `lib/domain/allocation.ts` | Algorithm orchestration (plain async function, no class) |
| `AssignmentsService.swapAssignments()` | `lib/domain/swap.ts` | Conflict validation, swap execution |
| `SwapRequestsService` | `lib/domain/swap.ts` | Swap state machine, matching logic |
| `ExportService` | `lib/domain/export.ts` | CSV/JSON export — unchanged logic, moved |

`lib/domain/` functions are plain async functions, no classes. They import from repositories and are imported by API routes.

### Phase 3 — EventRepository Split

Current `lib/repositories/event.repository.ts` is 536 lines with 5 distinct concerns. Split into 4 focused classes, all extending `BaseRepository`:

```
lib/repositories/
  event.repository.ts              ← CRUD + delete cascade (~150 lines)
  event-config.repository.ts       ← getConfig(), upsertConfig() (~60 lines)
  event-registration.repository.ts ← registrations CRUD + cleanup (~120 lines)
  event-metadata.repository.ts     ← templates + attributes (~150 lines)
```

Import paths in all API routes and domain functions updated to reference the correct split repo. Total line count stays similar — this is a split, not a reduction.

### Phase 4 — Cleanup

**useEventContext wrapper deletion:**
- `lib/hooks/useEventContext.ts` is a 12-line pure re-export wrapper with 40+ consumers.
- Automated find-replace: all import paths changed from `@/lib/hooks/useEventContext` → `@/lib/contexts/EventContext`.
- Test mocks updated in the same commit.
- File deleted.

**Cache trim:**
- Delete `lib/cache/types.ts` — inline `CacheEntry` type into `CacheProvider.tsx`.
- Delete `lib/cache/utils.ts` — inline `isCacheEntryValid()` into `useCache.ts`.
- The CustomEvent broadcast pattern (`CacheProvider`, `useCache`, `invalidateEventCache`, `invalidateIdentity`) is preserved — it does real cross-component coordination work.
- Net: −2 files, ~60 lines.

**Validation guard consolidation:**
- `assertEventStatusAllows()` currently lives in every service method.
- `event-status-permissions.ts` (`canRunAlgorithm()` etc.) is a separate helper.
- Both merge into `lib/domain/event-status.ts` — single import point for all callers.
- Zod schemas in route handlers remain (they are request-shape validation, not status guards — different concern).

## Sub-project B: Distribution & Analysis

**Status: DONE** (2026-07-27). Tagged `v2.5-b-distribution-control-center`. Engine: `canAssign()` gate in Phase 1+2, `reservedSlots`, structured `Violation[]`, dry-run + `redistributeScoped`. UI: `/admin/events/[id]/distribution` Control Center (heatmap, analysis table, redistribute overlay). APIs: preview, redistribute, analysis, heatmap data.

### Goal

Fix all three broken enforcement mechanisms (FILTER rules, BALANCE rules, maxShiftsPerPerson), and deliver the Distribution Control Center — a unified page for interactive assignment management, eligibility visualization, and distribution analysis.

### Sequencing (within B)

1. **Engine first** — Fix enforcement, add dry-run mode, add scoped redistribute
2. **UI second** — Build Control Center on top of the working engine

### B1: Distribution Engine Fixes

**Root cause:** No unified gate. Each algorithm phase has partial, inconsistent checks. Assignments can proceed despite constraint violations because no single function enforces all constraints together.

**Fix: `lib/algorithm/can-assign.ts`** — new unified gate called before any assignment in all three phases. Must be a pure function (no Prisma or server-only imports) — it is also evaluated client-side in the heatmap. Takes all inputs as parameters:

```typescript
function canAssign(
  memberId: string,
  shift: Shift,
  state: AssignmentState,
  config: EventConfig,
  rules: AllocationRule[]
): { eligible: boolean; reason?: string } {
  // 1. Max shifts cap
  if (state.memberShiftIds[memberId].length >= config.maxShiftsPerPerson)
    return { eligible: false, reason: "max_shifts" };

  // 2. Overlap / rest period
  if (hasTimeConflict(memberId, shift, state, config.minRestMs))
    return { eligible: false, reason: "time_conflict" };

  // 3. FILTER rules — hard block
  const filterRules = rules.filter(r => r.ruleKind === "FILTER" && r.shiftType === shift.type);
  if (!memberPassesAllFilterRules(memberId, filterRules))
    return { eligible: false, reason: "filter_rule" };

  // 4. Capacity
  if (state.shiftCoverage[shift.id] >= shift.capacity)
    return { eligible: false, reason: "capacity" };

  return { eligible: true };
}
```

**Changes per file:**

| File | Change |
|---|---|
| `lib/algorithm/can-assign.ts` | **New** — unified gate |
| `lib/algorithm/optimizer.ts` | All three phases call `canAssign()` before assignment; remove phase-specific partial checks |
| `lib/algorithm/rule-validator.ts` | `enforceBalanceReservation()` rewritten — reserve slots upfront at state init, checked inside `canAssign()` for relevant shift types |
| `lib/algorithm/validator.ts` | Post-allocation validation kept as integrity check, not primary enforcement |
| `lib/algorithm/types.ts` | Add `reservedSlots: Record<string, number>` to `AssignmentState` |

**Dry-run mode:**

`runAssignmentAlgorithm()` gains a `dryRun: boolean` flag. When `true`: runs all phases, collects assignments and violations, returns `{ assignments, violations }` without writing to DB.

**Violation shape:**
```typescript
type Violation = {
  kind: "max_shifts" | "filter_rule" | "balance_rule" | "capacity" | "min_shifts";
  memberId?: string;
  shiftId?: string;
  detail: string;
}
```

**New API routes:**
```
POST /api/events/[id]/assignments/preview       ← dry-run, returns { assignments, violations }
POST /api/events/[id]/assignments/redistribute  ← scoped re-run { memberIds, shiftIds }
GET  /api/events/[id]/distribution/analysis     ← flat table data
```

All three wrapped in `withAuth(withErrorHandling(...))`.

**Testing for engine:**
- Unit tests for `canAssign()` — one test per rejection reason.
- Integration tests for `runAssignmentAlgorithm()`: scenarios where previously all three constraints were violated — assert all enforced now.
- Dry-run test: assert no DB writes occur, violations reported correctly.
- Regression: existing algorithm tests must still pass (correct assignments not broken by new gate).

### B2: Distribution Control Center UI

**Page:** `app/admin/events/[id]/distribution/page.tsx`

The existing `DistributionSettings.tsx` is promoted into this page as one panel. The page adds the heatmap panel and analysis table panel alongside it.

**Layout:**
```
┌─────────────────────────────────────────────────────┐
│  Distribution Control Center         [Dry Run] [Run] │
├──────────────────────────┬──────────────────────────┤
│  HEATMAP                 │  ANALYSIS TABLE          │
│  Filter: [shift type ▾]  │  Filter: [violations ▾]  │
│  [member rows ×          │  Member | Shifts | Viol. │
│   shift columns]         │  ──────────────────────  │
│                          │  Bear   |  3/5  |  ⚠ 1  │
│  ● Eligible              │  Wolf   |  2/5  |  ✓    │
│  ★ Preferred             │  ...                     │
│  ✗ Blocked               │                          │
│  ■ Assigned              │                          │
│  ▲ Conflict              │                          │
│                          │                          │
│  [Redistribute           │                          │
│   Selection]             │                          │
└──────────────────────────┴──────────────────────────┘
```

**Heatmap cell states (two-tier eligibility):**

| State | Color | Meaning |
|---|---|---|
| `blocked` | Red | `canAssign()` returns false — hard constraint violation |
| `eligible` | Grey | Can assign, no preference |
| `preferred` | Green | Can assign + WANT preference |
| `assigned` | Blue | Currently assigned |
| `conflict` | Orange | Assigned but constraint now violated (plan changed after assignment) |

The two tiers map to the user's intent: Tier 1 = "can I safely assign?" (blocked vs. not), Tier 2 = "would they be happy?" (preferred vs. eligible).

**Heatmap interactions:**

- **Click eligible/preferred cell** → optimistic assign → `POST /api/events/[id]/assignments` → revalidates heatmap
- **Click assigned cell** → confirm dialog → unassign
- **Select cells/rows/columns** → toolbar: "Redistribute N selected" → `POST .../assignments/redistribute` with `{ scope: { memberIds, shiftIds } }` → dry-runs first, shows diff overlay, user confirms before committing
- **Scoped filters** — filter by shift type, time range, member attribute. Heatmap re-renders for visible subset. Filter state is URL-persisted (query params) so sharing a filtered view works.

**Analysis table columns:**
`Member | Assigned | Min | Max | Per-Type breakdown | Attribute coverage | Violations`

- Clicking a row highlights that member's column in the heatmap.
- Violation cells link to the specific heatmap cell.
- Sortable by any column. Filterable to show only violating members.

**Algorithm runner (promoted from DistributionSettings):**

- **Dry Run button** → `POST .../assignments/preview` → populates both panels with predicted state; violations highlighted in red; banner: "Preview — not committed. X violations found."
- **Run button** → confirm dialog → commits → both panels update from live state.
- Settings (weights, max shifts, rules) remain configurable in a collapsible settings panel on this page.

**Data flow:**

- Heatmap data: `GET /api/events/[id]/assignments` (existing) + preference data + member attributes + config/rules (via existing config route) — all fetched client-side, then `canAssign()` evaluated locally per cell. `canAssign()` is pure so this is safe.
- Analysis table: `GET /api/events/[id]/distribution/analysis` — server computes per-member aggregates and violations
- All mutations invalidate the `assignments*` and `members*` cache scopes via existing `invalidateEventCache()`

**Testing for UI:**
- Unit: cell state derivation (given `canAssign()` result + preference + assignment state → correct cell state)
- Unit: analysis table aggregation logic
- Integration: click-to-assign calls correct API, optimistic update rolls back on error
- Manual e2e: dry-run shows violations before commit; redistribute scoped to selected members only touches those members
