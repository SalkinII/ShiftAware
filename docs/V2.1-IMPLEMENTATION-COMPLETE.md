### **Phase 2: Core APIs (12 Tasks)**

#### Event Registration Endpoints
- `GET /api/events/[id]/registrations` - List registrations for event with member details
- `POST /api/events/[id]/registrations` - Register a member for event
- `GET /api/events/[id]/registrations/[memberId]` - Get specific registration
- `PUT /api/events/[id]/registrations/[memberId]` - Update registration status
- `DELETE /api/events/[id]/registrations/[memberId]` - Remove registration

#### Event Template Endpoints
- `GET /api/events/[id]/templates` - List assigned + event-specific templates
- `POST /api/events/[id]/templates` - Assign global template to event
- `DELETE /api/events/[id]/templates/[templateId]` - Unassign template from event

#### Enhanced Existing Endpoints
- **Shift Templates API** - Added `?eventId=` filter, supports event-specific templates
- **Members API** - Added `?eventId=&includeUnregistered=` filters
- **Preferences API** - Updated to use `wantLevel` enum, added upsert logic + DELETE

#### Swap Request Endpoints
- `GET /api/swap-requests` - List swap requests with filters (memberId, eventId, status)
- `POST /api/swap-requests` - Create swap request with auto-matching
- `GET /api/swap-requests/[id]` - Get swap request details
- `PUT /api/swap-requests/[id]` - Approve/decline swap (admin only)
- `DELETE /api/swap-requests/[id]` - Cancel pending swap request

**Auto-Matching Logic:**
When user A requests to swap from Shift X to Shift Y, the system checks if user B has a pending request to swap from Shift Y to Shift X. If found, both requests are automatically marked as `MATCHED` and await admin approval.

#### Verified Existing Features
- ✅ EventConfig GET/PUT endpoints save correctly
- ✅ Audit rollback POST endpoint functional
- ✅ Assignment algorithm endpoint exists (preview mode ready for UI)

## 🏗️ Architecture Achievements

### Event-Scoped Data Model
✅ **Many-to-Many Relationships**
- Members can register for multiple events
- Events can have multiple registered members
- Global templates can be assigned to multiple events
- Events can have event-specific templates

✅ **Proper Data Isolation**
- All queries can filter by `eventId`
- Members API returns only registered members for event
- Templates API returns assigned + event-specific only
- Preferences scoped to shifts within events

### API Design Principles
✅ **RESTful Conventions**
- Consistent HTTP methods (GET, POST, PUT, DELETE)
- Proper status codes (200, 201, 400, 403, 404, 409)
- Standardized error responses

✅ **Authorization**
- All endpoints check `isAuthenticated()`
- Admin-only operations check `isAdmin()`
- Proper 401/403 responses

✅ **Validation**
- Zod schemas for all request bodies
- CUID validation for IDs
- Enum validation for status fields

### Context Management
✅ **Persistent State**
- localStorage for identity selection
- Separate admin/user event context
- Automatic restoration on page load

✅ **Clean Separation**
- Admin uses `adminSelectedEventId`
- User uses `selectedEventId` + `selectedMemberId`
- Logout clears all stored context

## 💡 Key Technical Decisions

1. **Junction Tables** - Used proper many-to-many relationships instead of arrays
2. **Enum Migration** - Added default value to avoid breaking existing data
3. **localStorage** - Simple, effective for single-user desktop app context
4. **Auto-Matching** - Swap requests automatically match complementary requests
5. **Event Scoping** - All APIs accept `eventId` parameter for filtering
6. **Separate Contexts** - Admin and user have independent event selection
